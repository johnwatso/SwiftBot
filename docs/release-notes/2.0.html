SwiftBot 2.0

Version 2.0 · Requires macOS 26 or later on Apple silicon

SwiftBot 2.0 is our biggest release yet. It changes how you run, manage, and build with SwiftBot: a redesigned native Mac console, a complete browser interface for your server, an expanded automation engine, and a rebuilt foundation for backup, recovery, and recordings across Macs.

Your Mac hosts the bot. Your browser puts its features within reach from a phone, tablet, or desktop. With 2.0, those two sides work together around a clearer setup experience, more capable workflows, and better visibility into what SwiftBot is doing.

A redesigned native Mac console

The Mac app has been rebuilt around running SwiftBot and looking after its services. A simpler sidebar, consistent glass surfaces, clearer status, and dedicated service pages bring the console together.

  • Overview: this Mac’s identity, version, uptime, service health, quick actions, and system details in one place. Issues link to the relevant settings section.
  • Discord: connection controls, token management, auto-connect, invite links, permissions, known servers with their icons, and connection diagnostics.
  • Web Interface: clearer local and public addresses, tunnel status, transport details, and HTTPS policy. Cloudflare credentials and subdomain editing have their own sheets.
  • SwiftMesh: status and configuration together, with the cluster map, node identity, configured and current roles, and Health & Work cards.
  • Recordings: manage this Mac’s source folders and Fast Start copies, with folder availability, scan feedback, and an indexed-library summary.
  • Activity and Settings: search and filter logs by topic or severity, copy or export reports, and manage Launch at Login under Settings → General. Onboarding also adopts the console’s new visual language.

The Web Interface becomes your bot’s control centre

2.0 completes the move of bot feature configuration into the Web Interface. Configure your server from any browser while the native app handles the Mac, its credentials, and its connections.

The dashboard brings together Commands, Welcome Flow, Automations, Moderation, Events, Patchy, Sweep, Lookup, Announcer, Apple Intelligence, Game Tracker, Analytics, Rewind, and Recordings. Existing member access also gives server members their own Replay and the clips they appear in, when enabled by an administrator.

  • Run automation simulations, export or clear Activity, clear cached data, and manage SwiftMesh nodes from the browser.
  • Every channel picker supports type-ahead search, making large server lists easier to navigate.
  • Errors and success messages appear as visible notifications, including the reason a pairing or settings request failed.
  • Discord sign-in works when started from a local address and returns you to the page you were using. Expired sessions take you back to sign-in with a clear explanation.

Automations with branching, memory, and schedules

Automations can now make decisions, remember what happened, and run at a chosen time. Build richer workflows in the browser without writing code.

  • Nested conditions: combine AND, OR, and NOT groups instead of relying on a single flat list of filters.
  • Conditional steps: use nested If/Otherwise branches to choose different actions within the same rule.
  • Memory: named counters remember occurrences for a chosen period. Count by user, channel, server, or individual rule, and share counters across rules where needed.
  • Cooldowns: limit repeated runs by scope. Cooldowns and counter state are saved across restarts and included in SwiftMesh recovery.
  • Scheduling: run once, daily, weekly, or at an interval. Daily and weekly repeats use the selected time zone, including daylight-saving changes.
  • More live triggers: reaction and slash-command automations now receive real Discord events. Enabled automation commands register with Discord, while media triggers correctly start scanning.
  • A clearer editor: insert trigger-aware variables into messages, logs, and webhooks. Choose whether a failed step stops the run or allows later steps to continue.
  • Simulation and history: preview selected and skipped steps without sending messages or waiting through delays. Simulation uses a separate copy of counters and cooldowns. Recent runs show step traces, errors, waiting steps, and recovery status.

Delayed runs now continue independently, keeping incoming Discord messages, voice updates, and heartbeat acknowledgements moving while an automation waits.

A new Events page

Bring Discord Scheduled Events into your workflows. The new admin-only Events page lists events across connected servers and lets you prepare a rich announcement for each one.

  • Announce at the event’s start, a chosen amount of time before or after it, or an absolute custom date and time.
  • Include the event’s name, description, link, and start time using event variables, with an embed preview before saving.
  • Start-relative announcements follow event changes before their run is admitted. Cancelled, removed, or invalid events stop with a diagnostic, and removing an announcement cancels it.
  • Edited, disabled, or deleted scheduled workflows are checked again before sending. An already admitted event announcement is not repeated simply because the event moves.

Stronger moderation and clearer enforcement

  • New ban and remove-timeout actions join the existing moderation tools. Bans can optionally remove recent message history; the default preserves it.
  • Kick and ban reasons support variables and appear in Discord’s audit log. Invalid timeout or message-cleanup durations are rejected before a request is sent.
  • Search rules, filter enabled and disabled rules, and see specific action summaries, enforcement counts, and recent successful or failed moderation activity.
  • Ban templates start disabled, and saving or enabling a ban rule requires confirmation.
  • Live events share one moderation-first dispatcher. Destructive moderation suppresses ordinary automations for that event, preventing a normal reply from running ahead of a delete or ban.

SwiftMesh rebuilt for backup and recovery

2.0 expands SwiftMesh from pairing Macs into a more complete recovery system, with verified backup setup, coordinated transfers, saved automation progress, and clearer ownership.

  • Automatic backup setup: open the Primary’s Web Interface on the backup Mac and choose SwiftMesh → Pair SwiftBot → Continue in SwiftBot → Set Up Backup. Setup enrolls credentials, inherits Ruru settings when configured, verifies the connection, and completes the first sync before reporting that the backup is ready.
  • Coordinated return: the returning Primary catches up with shared state and credentials before the current owner closes its Discord connection and hands back control. Failed catch-up leaves the existing owner running.
  • Saved automation progress: delayed runs can resume from saved checkpoints after takeover. Actions whose outcome is uncertain are held as Needs review instead of being repeated automatically.
  • Better state synchronisation: shared configuration, automation memory, command cooldowns, and execution checkpoints are transferred with revision checks and recovery safeguards.
  • Resilient background work: worker jobs for AI replies, wiki lookups, and playlist imports gain persisted IDs, retry handling, duplicate checks, and local fallback.
  • Each Mac keeps its own setup: websites, tunnels, recording folders, companion apps, browser sessions, and passkeys stay local. Saving settings respects whichever Mac currently owns the bot.
  • A useful standby homepage: passive Macs show their role and connection status. The browser automatically restores the full dashboard on takeover and returns to the status page if ownership is lost.

Ruru integration and Preferred Primary

Optional Ruru integration gives both Macs an independent authority for deciding who may operate the bot, helping prevent competing owners when the Macs lose contact with each other.

  • Pair with Ruru using its address and a single-use short code, approve the request in Ruru, then review the connection in SwiftBot. Backup setup inherits the connection without a second Ruru code.
  • Choose a Preferred Primary in Ruru. SwiftBot uses coordinated handback to return to that Mac when it is healthy and ready.
  • See Ruru’s health, Current Owner, Preferred Primary, and lease status in SwiftMesh.
  • Temporary unanswered renewals are retried while the current lease remains valid. A Primary can recover automatically when Ruru returns, including after starting while it was unavailable.
  • Standbys with missing or mismatched Ruru configuration refuse takeover and explain why. Discord output stops when ownership permission expires.
  • Compatible Ruru versions can show standby and worker presence and include the current owner’s website in failover and recovery alerts.

One recording library across your Macs

Opt in to combine recordings from paired Macs in the active Primary’s Web Interface. Browse local and shared clips together by game or date and play them in the same browser player, even while the Mac storing a clip remains on standby.

  • Choose Share this Mac’s recordings during pairing, or enable it later under Recordings → Shared Library. The choice belongs to that Mac.
  • Each Mac uses its own recording folders and HTTPS website. SwiftBot requests website approval in Ruru and explains pending approval or missing setup.
  • Ruru helps discover the libraries; recording metadata and media are served by SwiftBot. Video does not pass through Ruru.
  • Missing folders and unreachable remote libraries retain clearly marked unavailable entries, with playback disabled until the source is available again.
  • Existing member permissions apply to shared clips too: members can play only recordings they appear in. Turning off sharing withdraws that Mac’s library.

A major Lookup overhaul

  • Lookup replies are now the wiki card itself, with Open on wiki and Not this one? buttons. Choose another matching page when the first result is wrong.
  • Query autocomplete suggests page titles, aliases, and frequently requested items.
  • Compare two items stat by stat using the slash command’s comparison option or a query such as “AKM vs FCAR”.
  • Improved site detection and infobox parsing support more Fandom, wiki.gg, table, and custom wiki layouts. THE FINALS uses a working API path, and text decoding fixes garbled summaries and fields.
  • Set per-source aliases, start from suggested wikis, and use Try it to preview the Discord card and choose its fields.
  • Reply caching reduces repeat requests. Usage statistics show weekly lookups, popular items, and recent misses.
  • With Answer questions in chat enabled, AI replies can consult a configured wiki for the item a question names before answering.

A richer Rewind archive

Rewind now records more of the context around your community’s activity alongside its message archive.

  • A new presence archive captures what members are doing while they are in voice, including game details and changes to maps, modes, or party information when Discord provides them.
  • A server journal records Discord events alongside the archive, preserving more of the server’s history.
  • Activity archiving follows Rewind’s enabled state and collection settings. Presence is recorded while a member is in voice, and in-progress segments are checkpointed for recovery after a restart.

Security and credentials throughout the new workflows

  • Automation webhook URLs move into macOS Keychain. Rules, saved runs, and shared snapshots carry credential references rather than token-bearing URLs; older files are migrated when loaded.
  • Webhook URLs are write-only in the editor and are not returned to the browser. Read-only viewers also receive redacted webhook content and credential references.
  • SwiftMesh credential transfers require an approved node’s identity proof in addition to mesh authentication. Private signing keys stay in Keychain, while approval lists contain public verification keys.
  • Public tunnel sign-in uses the supported Discord authentication flow. The developer fallback password is restricted to local access.
  • Shared recording requests retain viewer permissions and use approved destinations. Recording sharing authorises media reads without granting remote editing or export access.

More polish and fixes

  • YouTube music links are recognised alongside the other supported services. Richer music cards show album, year, length, source, and full-width artwork where available, with a clearer preview in the link watcher editor.
  • Music artwork hosts are allowed by the Web Interface’s image policy, and the preview dialog no longer clips the card.
  • Avatars for nicknamed members are cached at startup, and SwiftMiner’s Edit games modal submissions are now dispatched correctly.
  • Stopping a Primary no longer leaves its native settings incorrectly locked as though it were a standby.
  • Removed obsolete native feature views, the old rule store, and Remote Control infrastructure so the active console and Web Interface use the same automation state.

Upgrading from 1.x

Use the Mac app for host setup, connections, credentials, and local recording folders. Use the Web Interface for bot features, recording playback, and remote management. The classic native dashboard, native bot feature pages, and old Remote Control mode have been retired.

Update every SwiftMesh Mac to 2.0 so the nodes share the current recovery and credential-transfer behaviour, including webhook credentials after failover. Generate a fresh pairing invitation if an older backup lacks credential enrollment or your current Ruru configuration.

Shared recordings are optional and require each participating Mac’s own reachable HTTPS website and approval in Ruru. Recordings and Announcer remain beta features. SwiftMesh saves progress for recovery, but a sudden outage can still lose unsynchronised events or leave an action needing review.
